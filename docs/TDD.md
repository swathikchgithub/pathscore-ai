# Technical Design Document — PathScore AI

Companion to [PRD.md](PRD.md) (what/why) and [ARCHITECTURE.md](ARCHITECTURE.md)
(system diagrams) — this is the implementation-level design: data model, config
schema, API contract, algorithms, and known limitations.

## 1. Data model

Synthetic, generated by `src/synthetic_data_gen.py` with a fixed seed
(`np.random.default_rng(42)`) so labels are reproducible; `Faker()` for
display-only fields (`full_name`, `company_name`) is intentionally unseeded —
those never feed a model, only display.

**`data/synthetic/accounts.csv`** (entity: account)
`account_id, company_name, industry, company_size, icp_fit_score,
trigger_event, days_since_last_touch, existing_customer, any_converted,
max_prob, account_ptb_label, gtm_fit_label`

**`data/synthetic/contacts.csv`** (entity: contact)
`contact_id, account_id, full_name, title, buying_role, email_open_rate,
email_reply_count_90d, demo_requested, linkedin_engaged, avg_intent_score,
icp_fit_score, trigger_event, existing_customer, contact_converted,
true_conversion_prob, funnel_stage, funnel_stage_label`

**`data/synthetic/events.csv`**
`event_id, contact_id, event_type, intent_label, notes, days_ago` — `notes` is
a short templated snippet consistent with `intent_label`, standing in for raw
engagement text; `intent_label` is the *ground truth* signal used to build
labels below, `notes` is what the extraction layer (`build_features.py`) is
allowed to see instead.

### Label generation (`compute_ground_truth_labels`)

A single documented composite score drives three of the four labels:

```
z = 0.30 * avg_intent_score        (ground-truth, from events.intent_label)
  + 0.20 * email_open_rate
  + 0.15 * min(email_reply_count_90d / 5, 1)
  + 0.15 * icp_fit_score
  + 0.10 * role_weight              (economic_buyer=1.0 ... user_buyer=0.4)
  + 0.10 * trigger_weight           (none=0.0 ... compliance_mandate=0.25)
  + 0.05 * existing_customer
  + noise ~ N(0, 0.08)

conversion_prob = sigmoid(8 * (z - 0.5))
contact_converted  = Bernoulli(conversion_prob)
funnel_stage       = digitize(z, [0.35, 0.55, 0.75])   # MQL/SQL/Opp/Closed-Won
account_ptb_label  = any_converted AND icp_fit_score > 0.5   (rolled up from contacts)
gtm_fit_label      = icp_fit_score >= 0.65                    (independent of z)
```

`gtm_fit_label` is deliberately *not* derived from `z` — it's a threshold on
`icp_fit_score` alone, keeping GTM Fit's label independent of any
trigger/engagement signal by construction, matching its product definition
(PRD.md).

## 2. Pipeline stages

```
1. synthetic_data_gen.py     -> data/synthetic/{accounts,contacts,events}.csv
2. build_features.py         -> data/features/<use_case>.csv
3. train.py                  -> models/<use_case>/{model.joblib, calibrator.joblib, metrics.yaml}
4. app.py                    serves /score* from the trained artifacts (cached in-process)
5. run_scheduled_jobs.py     re-runs (2)+(3) [retrain] or (2)+drift_check [drift-check], on cadence
```

Stage 2 is where entity type decides the code path
(`build_features._select_builder`):

- **`entity: contact`** — `build_contact_features` calls `get_extractor(config)`
  once per *event* (not per contact) against `events.notes`, averages the
  resulting `intent_score` per contact, and replaces the raw
  `avg_intent_score` column with it. This is the actual call site for
  `CortexExtractor`/`LoRAExtractor` — see [ARCHITECTURE.md, §3](ARCHITECTURE.md#3-data-flow-synthetic-data-to-a-servable-model).
- **`entity: account`** — `build_account_features` is a pass-through read of
  `accounts.csv`; there's no text to extract from at the account level today.

## 3. Config schema (`src/config/*.yaml`)

| Key | Type | Meaning |
|---|---|---|
| `use_case` | str | Must match the filename stem; used as the models/features directory name. |
| `description` | str | Free text, shown nowhere programmatically today — documentation only. |
| `entity` | `contact` \| `account` | Selects the `build_features.py` code path. |
| `label_column` | str | Column in the raw/feature CSV that `train.py`/`drift_check.py` predict. |
| `id_column` | str | Column used as the leaderboard's row identifier. |
| `sample_data` | path | CSV the `/leaderboard` route scores (currently the raw synthetic file). |
| `feature_columns` | list[str] | Exact columns fed to the model, in order. |
| `categorical_columns` | list[str] | Subset of `feature_columns` cast to `category` dtype for LightGBM. |
| `model.type` | str | Informational only — `train.py` always instantiates `lgb.LGBMClassifier`. |
| `model.params` | dict | Passed straight through to `LGBMClassifier(**params)`. |
| `calibration.method` | `platt` \| `isotonic` | Maps to `CalibratedClassifierCV(method="sigmoid"\|"isotonic")`. |
| `positive_class` | any (optional) | Which class's probability is `score_pct`/SHAP factors; defaults to `max(classes)`. |
| `retrain.cadence` | str | Documentation only — the actual cadence lives in `.github/workflows/retrain.yml`'s cron. |
| `retrain.min_new_labels` | int | Consumed by `drift_check.py`: skips the check below this row count. |
| `retrain.drift_check_metric` | `auc_roc` \| `precision_at_k` | Which metric `drift_check.py` recomputes and compares to baseline. |
| `retrain.drift_threshold` | float | Drift flagged when the metric drops by more than this. |
| `extraction.backend` (optional) | `cortex` \| `lora` | Contact-entity only; defaults to `cortex` when the whole `extraction` key is omitted. |
| `extraction.hf_endpoint_url`, `extraction.adapter_name` | str | Required only when `backend: lora`. |

No config currently sets `extraction` at all — both contact-entity use cases
default to Cortex ([ADR-0003](adr/0003-cortex-first-lora-fallback.md)). Config
validation is implicit: a missing required key fails wherever it's first read
(e.g. `KeyError` in `train.prepare_data`), not against an upfront schema — see
Known Limitations.

## 4. API contract (`src/serving/app.py`)

| Route | Auth\* | Success | Failure modes |
|---|---|---|---|
| `GET /health` | none | `200 {"status": "ok"}` | — |
| `GET /use-cases` | none | `200 ["contact_score", ...]` | — |
| `POST /score/{use_case}` | API key + rate limit | `200 ScoreResponse` | `401` (bad/missing key), `404` (unknown use case / model not trained), `422` (malformed body / missing feature columns), `429` (rate limit) |
| `GET /score/{use_case}/leaderboard?limit=N` | API key + rate limit | `200 LeaderboardResponse` | `401`, `404` (unknown use case / model not trained / no `sample_data`), `429` |

\* Auth/rate-limit only enforced when `API_KEY`/`RATE_LIMIT_PER_MINUTE` are
configured — see [ADR-0008](adr/0008-api-key-rate-limit-over-full-auth.md).

```
ScoreResponse:
  use_case: str
  score_pct: float              # positive_class probability, 0-100, 2dp
  predicted_class: str          # argmax class, stringified
  class_probabilities: dict[str, float]
  top_factors: list[{feature: str, impact: float}]   # top 5 by |SHAP value|

LeaderboardResponse:
  use_case: str
  count: int
  results: list[{id: str, ...ScoreResponse fields}]   # sorted score_pct desc
```

`limit` is clamped to `[1, 500]` server-side regardless of what's requested.

## 5. Algorithms and complexity

Stated per this repo's own convention (every non-trivial algorithm declares
its complexity, see `CLAUDE.md` §7):

| Function | Time | Space | Note |
|---|---|---|---|
| `_score_batch` (app.py) | O(n) | O(n·f) | One batched `predict_proba` + one batched `shap_values` call for all n rows, f features — not n separate model invocations. |
| `precision_at_k` / `_multiclass` | O(n log n) | O(n) | Dominated by `argsort` to rank by predicted score. |
| `assert_no_leakage` | O(n·f) | O(1) extra | One correlation pass per numeric feature column. |
| `_extract_contact_intent` | O(e) | O(k) | e = event rows (one extractor call each), k = distinct contacts for the groupby-mean aggregate. |
| `enforce_rate_limit` | O(w) per request | O(keys × w) | w = requests for that key in the trailing 60s window, bounded by `RATE_LIMIT_PER_MINUTE`. |

## 7. Security model

- **Input validation:** Pydantic (`ScoreRequest`) for shape; `_build_feature_frame`
  checks every configured `feature_columns` entry is present before indexing,
  returning `422` naming what's missing instead of an uncaught `KeyError`.
- **Auth:** optional shared `API_KEY`, constant-time compared
  (`secrets.compare_digest`) — see ADR-0008.
- **Rate limiting:** in-process fixed window, keyed by API key or client IP.
- **CORS:** `CORS_ORIGINS` env var, `*` by default (no `allow_credentials`, so
  the wildcard doesn't expose cookie/session data — there is none).
- **Secrets:** `SNOWFLAKE_*`, `HF_API_TOKEN`, `API_KEY` are env-var only,
  never hardcoded; `.env`/`.env.local` gitignored; `.env.example` documents
  every var without real values.
- **Prompt injection:** `CortexExtractor.extract` wraps untrusted email text in
  an explicit `<email>...</email>` tag and instructs the model to treat it as
  data, not instructions — see `intent_extractor.py`.

## 8. Known limitations

- **Feature store is a flat CSV snapshot**, not versioned or point-in-time —
  see [ADR-0005](adr/0005-flat-csv-feature-snapshots.md).
- **`drift_check.py` compares against the same static synthetic dataset** on
  every run today; it's only meaningful once real, time-varying labeled data
  replaces the synthetic generator (documented in the module's own docstring).
- **`LoRAExtractor`'s mock has no adapter-specific behavior** — there's no real
  trained adapter to approximate (ADR-0002).
- **No config schema validation upfront** — a malformed `src/config/*.yaml`
  fails wherever the missing/wrong-typed key is first read, not at load time.
- **Rate limiter is single-worker/in-process** — a multi-worker deployment
  needs a shared store (Redis) instead (ADR-0008).
- **`Faker()` is unseeded** — `full_name`/`company_name` differ on every
  regeneration; cosmetic only, neither is a feature column.
